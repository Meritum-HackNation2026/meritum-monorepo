# AGENTS.md

Guidance for AI coding agents (and humans who run them) working on Meritum. The product is
described in `design-system/docs/product-doc.html` (generated by `gen_product_doc.py`): user
stories `US-XXX-NN`, features `F-NN`, decisions `ADR-NN`.

## Repositories

This repo pins the others as submodules. Each code repo is worked on in its own checkout or
worktree; issues and PRs live in the repo whose code changes.

| Path | Repo | What |
|---|---|---|
| `core/` | meritum-core | contracts, ports, adapters, factories, pure domain rules |
| `backend/` | meritum-backend | FastAPI API and inbound channels (WWW, Discord, SMS, MCP) |
| `worker/` | meritum-worker | DBOS workflows (check pipeline, ingestion, retention, evaluation) |
| `frontend/` | meritum-frontend | web app: form, result card, moderator panel, evaluation page |
| `extension/` | meritum-extension | Chrome MV3 extension (WXT) |
| `mocks/` | meritum-mocks | platform mocks and the Discord mock (Hono) |
| `infra/` | meritum-infra | deployment (GCP, on-prem runners) |
| `design-system/` | meritum-design-system | product document, copy, tokens, contract copy |
| `marketing/` | meritum-marketing | contest materials |
| `org-profile/` | .github | org profile, issue forms, PR template |

Integration branch per repo: `develop` in meritum-backend, meritum-worker and meritum-frontend;
`main` in every other repo (core, mocks, extension, docs, infra, design-system, marketing, this one).
Branches: `<type>/<issue>-<slug>` from the integration branch → PR to it. In backend, worker and
frontend a human then promotes `develop` → `main`; elsewhere the merge to `main` is the release.
Never push to `develop` or `main`.

## Skills

Read the matching skill **before** the task. They live in `.claude/skills/`:

| Skill | When |
|---|---|
| [meritum-issue-writing](.claude/skills/meritum-issue-writing/SKILL.md) | filing, splitting or rewriting issues and epics |
| [meritum-issue-claiming](.claude/skills/meritum-issue-claiming/SKILL.md) | picking, starting, blocking or stopping work on an issue (mandatory for every agent) |
| [meritum-pr-review-loop](.claude/skills/meritum-pr-review-loop/SKILL.md) | opening a PR and every review round until merge or escalation |
| [meritum-architecture](.claude/skills/meritum-architecture/SKILL.md) | writing or reviewing any code |
| [meritum-ui](.claude/skills/meritum-ui/SKILL.md) | anything visual: web app, panel, extension, mocks, slides, marketing (design system is mandatory) |

`marketing/` and `design-system/` have their own `AGENTS.md`: visual material there also follows
four project-scoped design skills (frontend-design, impeccable, design-taste-frontend,
emil-design-eng), restored from `skills-lock.json`, with the design system taking precedence.

Engineering skills from the `mattpocock-skills` plugin, invoked by the Meritum skills at the
step that needs them:

| Skill | Step |
|---|---|
| `mattpocock-skills:tdd` | building, and fixing review findings that change behaviour |
| `mattpocock-skills:diagnosing-bugs` | `bug:` issues and failures with no obvious cause |
| `mattpocock-skills:code-review` | self-review before the PR; its two axes split each review round |
| `mattpocock-skills:pr` | the PR body, inside the org template |
| `mattpocock-skills:wizard` | a blocker that only a human can clear |
| `mattpocock-skills:grilling` | issue writing with a human in the session |
| `mattpocock-skills:writing-for-agents` | editing a skill, `AGENTS.md` or `CLAUDE.md` |

Where one of them disagrees with a Meritum skill or an architecture check, the Meritum side wins.

The plugin is enabled for this repo in `.claude/settings.json`; install it once per machine:

```bash
claude plugin install mattpocock-skills@claude-plugins-official --scope project
# worktree outside this repo, or headless runner: install at user scope (drop --scope project);
# if the marketplace is unknown: claude plugin marketplace add anthropics/claude-plugins-official
```

## The workflow end to end

1. **Plan.** Stories and features in the product document become issues
   (meritum-issue-writing). Drafts are in `issues/drafts/` (index: `issues/drafts/README.md`);
   `scripts/publish-issues.sh` files them, `scripts/setup-labels.sh` creates the labels in
   every repo. New issues start in `status: triage`.
2. **Accept.** A human reads the issue and moves it to `status: ready`. Agents never start on
   `status: triage`.
3. **Claim.** An agent picks a ready, unassigned issue whose dependencies are closed, claims it
   with labels and a `Claimed by <agent>, branch <branch>` comment, and re-checks for a race
   (meritum-issue-claiming).
4. **Build.** In its own worktree, on `<type>/<n>-<slug>` from the integration branch, test-first in vertical
   slices (`mattpocock-skills:tdd`): the behave scenario from the issue's Gherkin goes red, then
   one unit test and one minimal change per cycle until it is green, following
   meritum-architecture (and meritum-ui for anything visual). A `bug:` issue starts with
   `mattpocock-skills:diagnosing-bugs` (meritum-issue-claiming, step 4).
5. **PR.** Self-review with `mattpocock-skills:code-review`, then a PR to the integration branch with
   `Closes #<n>`, issue moved to `status: in review`.
6. **Review.** Each round, two fresh reviewer subagents, one per axis (Standards: architecture
   and UI rules; Spec: the issue), given the diff and not the author's conclusions, post reviews
   with required fixes; the author fixes; at most 3 rounds tracked with `review: round 1|2|3`
   (meritum-pr-review-loop).
7. **Merge or escalate.** Approved and green: merge to the integration branch. Not approved after round 3:
   `review: needs human` with a summary. Humans promote `develop` to `main` in backend, worker
   and frontend.

Parallel agents: one issue per agent, one worktree per agent, a unique agent name per session
(`claude/<role>-<topic>-<k>`). An agent that dispatches subagents gives each one an issue
number and this file; each subagent claims its own issue.

## Hard rules

- Claim before coding; release or hand off when you stop. Never leave `status: in progress` behind.
- The author never approves its own PR; round 1 is always an independent review.
- No AI attribution in commits, PRs, issues or comments (no `Co-Authored-By` for an AI, no
  "Generated with", no robot emoji, no session links). Run PR and commit text through a
  humanizer skill when one is available.
- UI uses the Meritum design system only (tokens, Archivo/Azeret Mono, components, `copy/pl.json`);
  the only exception is the per-platform skins of the widget and mocks (meritum-ui).
- Contracts change only in meritum-core (ADR-02); the copy in design-system is synced, never edited.
- No secrets, tokens, real personal data or the hidden jury set in code, issues or logs.
- Never add e2e tests or tests needing contact between components (backend ↔ worker,
  frontend ↔ backend, cross-service database, browser e2e) to any CI workflow; they run
  manually or locally via a script. Reviewers reject CI changes that add them.
- Do not create tags, releases or the `develop` → `main` PR unless a human asks.

## Language

Code, identifiers, docstrings, skills and commit scopes: English. Issues, PR descriptions,
user-facing copy and READMEs: Polish (as the rest of the project).
